# Руководство для агентов разработки

## Назначение проекта

`INNtoPhone` автоматизирует обогащение карточек новых клиентов в CRM СБИС:

1. Получает ежедневно обновляемый список новых клиентов из CRM.
2. Извлекает и проверяет ИНН.
3. Запрашивает контактные данные через согласованный интерфейс Telegram-бота.
4. Проверяет и нормализует найденные контакты.
5. Записывает результат обратно в карточку клиента через API CRM СБИС.

Рабочий план и критерии готовности находятся в `docs/PROJECT_PLAN.md`.

## Текущий статус

Проект находится на этапе проектирования. Для прототипов выбран Python, а тестовый
Telegram-бот реализован на aiogram 3. Контракты API и способ интеграции
с целевым Telegram-ботом еще должны быть подтверждены. Не придумывайте методы API,
форматы полей, лимиты или способы авторизации: фиксируйте их только по официальной
документации и результатам проверки на тестовом контуре.

## Архитектурные границы

Разделяйте код по ответственности:

- `src/integrations/sbis/` — чтение и обновление данных CRM СБИС;
- `src/integrations/telegram/` — взаимодействие с Telegram;
- `src/domain/` — модели, нормализация ИНН и контактов, бизнес-правила;
- `src/application/` — сценарий обработки клиента и пакетного запуска;
- `src/storage/` — состояние запусков, идемпотентность и журнал ошибок;
- `src/cli/` — ручной запуск, диагностика и повторная обработка;
- `tests/` — модульные и интеграционные тесты;
- `docs/` — решения, схемы данных и эксплуатационные инструкции.

Направление зависимостей: интеграции зависят от доменных интерфейсов, а доменная
логика не зависит от SDK, HTTP-клиентов, базы данных или планировщика.

## Обязательные правила реализации

- Обработка должна быть идемпотентной: повторный запуск не создает дубликаты и не
  перезаписывает подтвержденные пользователем данные без явного правила.
- Идентификатор клиента из CRM является основным ключом операции; ИНН может
  повторяться у разных карточек и не должен быть единственным ключом.
- Перед запросом проверяйте ИНН по длине и контрольным цифрам.
- Телефоны храните и передавайте в нормализованном формате, сохраняя исходное
  значение отдельно только при реальной необходимости.
- Обновляйте только разрешенные поля карточки. Используйте optimistic locking,
  версию записи или повторное чтение перед записью, если API это поддерживает.
- Для временных ошибок применяйте ограниченные повторы с exponential backoff и
  jitter; постоянные ошибки отправляйте в очередь ручного разбора.
- Учитывайте rate limits обеих интеграций. Не обходите ограничения сервисов.
- Один сбой клиента не должен останавливать обработку всего дневного списка.
- Сохраняйте итог каждого шага: `pending`, `in_progress`, `enriched`, `not_found`,
  `needs_review`, `failed` или эквивалентные состояния.
- Структурные логи должны содержать correlation ID, идентификатор запуска,
  идентификатор клиента и этап, но не полные телефоны, токены или ответы сервиса.

## Безопасность и персональные данные

- Не добавляйте в Git токены, cookie, сессии Telegram, пароли, реальные выгрузки,
  дампы CRM, номера телефонов и иные персональные данные.
- Секреты берите из переменных окружения или утвержденного хранилища секретов.
  В репозитории допустим только `.env.example` без рабочих значений.
- Маскируйте телефоны и персональные данные в логах, тестах и сообщениях ошибок.
- Используйте минимально необходимые права API и отдельные учетные данные для
  разработки, тестового контура и production.
- До production подтвердите правовое основание обработки контактов, допустимость
  источника данных, сроки хранения и порядок удаления персональных данных.
- Не автоматизируйте пользовательский Telegram-аккаунт и не имитируйте клиента,
  пока такой способ явно не разрешен правилами сервиса и владельцем системы.

## Работа с изменениями

- Сначала изучите существующий код и ближайшие тесты; сохраняйте принятые в
  проекте соглашения.
- Делайте небольшие изменения в пределах одной ответственности. Не смешивайте
  новую функцию с несвязанным рефакторингом.
- Изменение контракта внешнего API сопровождайте обновлением адаптера, фикстур,
  тестов и документации.
- Для неоднозначных бизнес-правил сначала добавьте решение в документацию или
  запросите уточнение; не кодируйте догадку как факт.
- Не удаляйте и не откатывайте пользовательские изменения без явного запроса.

## Проверки

Установите текущие зависимости и запустите тесты командами:

```powershell
python -m pip install -r requirements.txt
python -m unittest discover -s tests -v
```

Запуск Telegram-бота-заглушки описан в `docs/TELEGRAM_STUB_BOT.md`.

Минимальное покрытие должно включать:

- валидацию ИНН организаций и ИП;
- нормализацию и отбраковку телефонов;
- отсутствие повторного обогащения при повторном запуске;
- ответы `not found`, несколько контактов, rate limit и временные ошибки;
- частичный отказ пакетной обработки и безопасный повтор;
- запрет обновления карточки при неполных или сомнительных данных;
- контрактные тесты адаптеров на обезличенных фикстурах.

Интеграционные тесты по умолчанию не должны обращаться к production-сервисам.

## Критерии завершения задачи

Задача готова, когда реализация соответствует бизнес-правилу, тесты для ее риска
добавлены и проходят, документация обновлена, а логи и фикстуры не раскрывают
секреты или персональные данные. В отчете явно указывайте, какие проверки были
выполнены, а какие не удалось запустить.
