# Бот отчетов

## Назначение

Отчетный бот использует отдельный Bot API token и ту же SQLite-базу, что и
ежедневный конвейер. Он не выполняет поиск контактов и не вызывает API СБИС.

Ежедневный отчет строится по `registration_date = today - 7 days`. Пользователь
из whitelist также может нажать «Отчет по дате» и выбрать день в календарной
inline-клавиатуре. Для каждого дня показано `обработано/всего`, включая дни без
организаций (`0/0`). Стрелки переключают календарные месяцы. Команда
`/report YYYY-MM-DD` сохранена как дополнительный прямой способ вызова.

## Разделы отчета

- контакты найдены;
- контакты не найдены;
- требуется ручная проверка;
- техническая ошибка, будет повтор;
- еще не обработано — только агрегированное количество.

В Telegram для каждой организации показываются только название, дата
регистрации, первый объединенный телефон и первая объединенная почта. При наличии
дополнительных значений выводится «и еще N». Российский телефон форматируется как
`+7 (999)-999-99-99`.

Полный Excel автоматически прикладывается сразу после краткого отчета. В нем
контакты списка СБИС, персонализированные контакты карточки и результат Telegram
остаются в отдельных колонках вместе со статусами и техническими кодами. Этот
формат одинаков для ручного и ежедневного отчетов, дополнений и повторной
доставки.

## Доступ и подписки

Права определяются только числовым Telegram user ID, а не username. Списки
пользователей и администраторов хранятся раздельно. Bootstrap-администраторы
задаются в `.env` и не могут быть удалены командами бота.

Добавление пользователя не включает подписку автоматически. Пользователь должен
сам открыть личный чат, выполнить `/start` и нажать «Подписаться». При удалении
последнего права доступа подписка отключается.

Каждая команда и callback повторно проверяют права. Группы и каналы не
поддерживаются, чтобы контактные данные не публиковались за пределами личного
чата.

Удаление пользователя, выдача роли администратора и снятие этой роли требуют
одноразового inline-подтверждения. Оно действует 5 минут, привязано к
инициировавшему его администратору и не содержит Telegram ID в callback-данных.

## Надежность

Запуск отчета уникален по виду, дате выборки и ревизии. Доставка учитывается для
каждого подписчика отдельно. Повторный запуск пропускает успешные доставки и
может повторить неудачные. Административный аудит не содержит Telegram ID в
открытом виде, ФИО, телефонов, почт или текста отчета.

Временные ошибки доставки повторяются с exponential backoff и небольшим
детерминированным jitter. Автоматический лимит — 5 попыток; постоянные ошибки
доступа и исчерпанные попытки остаются в состоянии ошибки для ручной проверки.

Для многочастного сообщения и приложенного Excel отдельно сохраняется состояние
каждой части. После сбоя повтор продолжается с первой недоставленной части. Excel
строится из сохраненного снимка, поэтому файл соответствует сообщению даже
после последующего изменения карточки. Каждый ручной запрос по дате атомарно
создает новую ревизию снимка из текущего состояния SQLite. HTML-сообщение и его
приложенный Excel используют одну ревизию и не расходятся при последующем изменении
карточки.

Перед первой автоматической отправкой сохраняются точные части сообщения.
Повтор после сбоя продолжает тот же текст с первой недоставленной части. У Bot
API остается узкое окно: если процесс завершится после принятия сообщения
Telegram, но до фиксации его ID в SQLite, одна часть может быть отправлена
повторно.

Если ранее включенная в отчет карточка позднее получила новый результат
обработки, следующий ежедневный запуск отправляет отдельное дополнение и снова
помечает карточку как отраженную в отчете.

Изменение только технического `result_code` или `error_code` без изменения
статуса, данных карточки либо контактов не создает отдельную рассылку. Актуальный
технический код остается доступен в новом ручном отчете по дате.

Остаток запросов поискового бота передается отчетной подсистеме из существующего
этапа обогащения. При переходе ниже `REPORT_LOW_QUERY_THRESHOLD` администраторы
получают одно предупреждение; при переходе к нулю — отдельное уведомление.
Пополнение баланса сбрасывает состояние предупреждения.
Ошибка чтения баланса также уведомляет администраторов только один раз до
следующей успешной проверки.

Администратор может выполнить `/pipeline_status` или нажать «Состояние
конвейера». Бот показывает только эксплуатационные данные: состояние запуска,
целевую дату, время начала и завершения, количество карточек, агрегаты статусов,
остаток запросов и технический код ошибки без названий, ФИО и контактов.

Рекомендуемый срок хранения снимков задается `REPORT_RETENTION_DAYS=90`. Пустое
значение или `0` отключает автоматическую очистку. После отчетного этапа
ежедневный конвейер удаляет более старые снимки, сохраненные части сообщений и
состояния доставки. Исходные карточки `new_clients` при этом не удаляются.
